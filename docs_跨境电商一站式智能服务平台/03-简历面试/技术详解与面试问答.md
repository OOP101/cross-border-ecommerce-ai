## 一、简历技术点详解

### 1. RAG 检索增强生成

**是什么**：先从外部知识库检索相关片段，拼进 Prompt 再让 LLM 生成，让回答「有据可依、可溯源」，而非只靠模型参数记忆。

**项目实现**（`services/chat.py` + `services/rag/`）：
- 知识入库：上传文档 → 按扩展名解析（PDF/DOCX/MD/TXT/CSV）→ 清洗去噪 + PII 脱敏 → **语义分块**（优先按段落/句子边界切，块上限 500 字、重叠 128 字，避免句中截断）→ Embedding → 向量库。
- 问答：意图识别 → 混合检索 → 上下文拼接（每个片段带 `[片段i · 来源:xxx]` 标记）→ LLM 生成 → 返回答案 + 来源列表（文件名、相似度、片段摘要）。

**为什么这么做**：商业客服场景不能接受幻觉；溯源 + 「知识库无相关信息时如实说明并建议转人工」的系统提示词双重兜底。

### 2. 混合检索（Hybrid Retrieval）：向量 + BM25 + RRF + 重排序

**为什么不用纯向量检索**：向量擅长语义相似（"怎么退货" 命中 "售后流程"），但对**专有名词、缩写、型号**等精确关键词弱（"L/C" "FOB"）；BM25 相反。外贸场景术语密集，必须双路互补。

**项目实现**（`services/rag/retriever.py`）：
1. 向量召回：query 向量与全部 chunk 余弦相似度，取 top_k×3；
2. BM25 召回：纯 Python 实现（`rag/bm25.py`，含 k1/b 参数与 IDF），无外部依赖；
3. **RRF 融合**：`score = Σ weight / (k + rank)`（k=60），只看排名不看原始分——巧妙避开了向量余弦分和 BM25 分**量纲不可比**的问题；
4. 可选重排序：关键词覆盖率与向量分的加权（`rag/rerank.py`），接口预留了替换为 bge-reranker / Cohere 的空间。

**中文分词适配**（`utils/text_utils.py`）：英文按单词、中文按相邻二字 bigram——单字无语义、整词太稀疏，bigram 是中文检索的常用折中。

### 3. 可插拔抽象层（工厂模式）

**项目实现**（`core/llm|embeddings|vector_store`，各有 `base.py` + `factory.py`）：LLM、Embedding、向量库、Agent 四个维度全部接口隔离。工厂读取 `.env` 配置返回对应实现；`openai_compatible` 实现同时兼容 DeepSeek、通义千问、OpenAI、Moonshot；**Key 缺失时自动降级 Mock** 并告警。

**为什么**：开发/演示/生产环境割裂是 LLM 应用的常见痛点。Mock 降级保证无 Key、无外网时全链路可跑通（CI、面试现场演示都不怕），配置切换即上真实模型。

### 4. SSE 流式输出

**是什么**：Server-Sent Events，基于 HTTP 的单向服务器推送，`Content-Type: text/event-stream`，天然兼容现有网关/CORS 体系。

**项目实现**（`api/v1/chat.py` `/chat/stream` + `core/llm/openai_compatible.py`）：
- LLM 层 `generate_stream`：请求 `stream=true`，逐行解析 `data: {...}` 取 `delta.content`，`[DONE]` 结束；
- 接口层：意图识别和检索（快）在流开始前完成，然后逐段推送 `event: delta`，最后推送 `event: meta`（意图、溯源、耗时、conversation_id）并落库——**先出首字再慢慢生成**，长回答等待感大幅降低；
- 落库用独立 `SessionLocal()`：流式响应结束时 FastAPI 依赖注入的 db 会话已关闭，这是一个容易踩的坑。

**SSE vs WebSocket**：客服问答只需服务器→客户端单向推送，SSE 更轻（纯 HTTP、自动重连、无协议升级）；需要双向（语音、协作）才用 WebSocket。

### 5. asyncio 并发生成

**简历表述**：文案"一键生成"要产出标题、描述、广告语、SEO 标签 4 段，串行延迟 = 4 段之和。

**项目实现**（`services/copywriting.py`）：`asyncio.gather` 并发 4 个 `agenerate`（`openai_compatible.py` 用 `httpx.AsyncClient` 真异步），总延迟降为**最慢一段**；用量统计在 gather 后统一落库。批量接口保持同步语义（每商品内部并发）。

**并发安全要点**：SQLAlchemy Session 非线程安全，但 asyncio 单线程事件循环中协程只在 `await` 处切换，每段的 `db.add/commit` 是同步连续执行的，因此同一线程内共享 Session 安全。

### 6. 两级翻译记忆（LRU + SQLite 持久化）

**项目实现**（`services/translation.py` + `db/models.py TranslationMemory`）：
- 一级：进程内 `OrderedDict` LRU（上限 1 万条，`move_to_end` + `popitem(last=False)` 实现）；
- 二级：SQLite 表（源文本 md5 为唯一键），进程重启 LRU 清空后回源数据库；
- 命中直接返回，**同句重译零模型调用成本**且译法绝对一致。

**为什么两级**：LRU 管"快"，持久化管"不丢"；只放内存重启即失效（且无上限会泄漏），只放数据库每次查询有 IO。

### 7. BM25 索引缓存与向量矩阵缓存（检索性能优化）

**问题**：最初实现每次提问都 `list_all()` 全量分词 + 重建 BM25，向量检索每次 `np.stack` 重拼矩阵——知识库增长后延迟线性劣化。

**项目实现**：
- BM25 按**语料指纹**（全部 chunk id 的元组）缓存（`retriever.py`），文档增删时调用 `invalidate_bm25_cache()` 失效重建——查询 O(1) 命中，增删 O(重建)；
- 向量库缓存**行归一化矩阵**（`vector_store/memory.py`），增删/加载时置 `None` 惰性重建；查询只剩一次矩阵×向量乘。

**面试点**：这是典型的"读多写少"缓存模式，失效时机挂在写路径上，不需要 TTL。

### 8. JWT 鉴权（PBKDF2 + HS256，零第三方依赖）

**项目实现**（`core/security.py` + `api/v1/auth.py`）：
- 密码：PBKDF2-HMAC-SHA256、10 万轮、16 字节随机盐，`hmac.compare_digest` 防时序攻击；
- 令牌：HS256 手写实现（header.payload.signature，base64url），校验签名与 `exp`；
- 角色：注册由服务端固定 `operator`（**防自助提权**），管理员经 `POST /auth/grant-role` 授予角色；`AUTH_REQUIRED` 开关兼容演示模式（免登录返回默认主体）。

**安全漏洞修复案例（面试好素材）**：评审时发现原注册接口 `role=req.role or "operator"` 直接信任客户端——任何人可传 `role=admin` 自助提权。修复：服务端强制角色 + 敏感操作要求当前用户为 admin + 接口级 403。

### 9. CORS 白名单自适应

**问题**：`allow_origins=["*"]` 与 `allow_credentials=True` 组合会被浏览器直接拒绝（规范禁止），携带凭据的跨域请求全部失败。

**项目实现**（`main.py`）：origins 为显式白名单时才开启凭据；通配符（演示模式）自动降级 `allow_credentials=False`。

### 10. FastAPI / SQLAlchemy 2.0 / pydantic-settings

- **FastAPI**：自动 Swagger、依赖注入（`Depends(get_db)` 会话生命周期）、`lifespan` 启动时建表与播种；
- **SQLAlchemy 2.0**：`Mapped`/`mapped_column` 新式类型注解 ORM；7 张表（知识文档/对话/反馈/用量/审计/用户/术语/翻译记忆）；轻量迁移用 `ALTER TABLE` 兼容旧库（如 `knowledge_docs.doc_id` 列）；
- **pydantic-settings**：全部配置 `.env` 可覆盖、类型校验、`lru_cache` 单例。

### 11. 前端（Vue 3 + Element Plus）

- axios **请求拦截器**注入 Bearer 令牌、**响应拦截器**统一错误提示 + 401 清凭据踢回登录页（登录页自身跳过防循环）；
- **路由守卫**：无本地用户信息时调 `/auth/me` 校验，演示模式直接放行；
- SSE 消费：`fetch` + `ReadableStream` reader 手动解析 SSE 帧（`event:`/`data:`），按 `\n\n` 分帧、缓冲区保留半帧，实现打字机渲染；
- 状态无全局 store 需求，登录态用 localStorage + 轻量模块函数管理。

### 12. 测试与工程化

- 冒烟测试 8 项（`tests/test_smoke.py`，TestClient 走全链路）+ 单元测试 14 项（`tests/test_units.py`：分块/分词/BM25/重排序无字段泄漏/JWT 往返与篡改/用量提取降级/Mock 流式/向量库增删查/**LLM 故障转移判定与端点顺序**）+ 租户隔离 3 项（`tests/test_tenant.py`），共 25 项，零新增依赖直接 `python tests/xxx.py` 运行；

### 13. 多厂商接入与 LLM 故障转移（高可用）

**背景**：单一 LLM 厂商就是单点故障——限流、宕机、密钥失效都会让整个平台不可用；且不同模型在不同任务上各有优劣。

**多厂商接入**（全部走 `openai_compatible` 协议实现，换厂商只改 `.env` 三行）：

| 厂商 | Base URL | 模型（以控制台实际 ID 为准） | 备注 |
|------|----------|------------------------------|------|
| 小米 MiMo（当前主端点） | `https://api.xiaomimimo.com/v1` | `mimo-v2.5-pro`（V2 系列 2026-06-30 已下线） | 鉴权用 `api-key` 头，我们同时发 Bearer 兼容 |
| DeepSeek（当前备用） | `https://api.deepseek.com/v1` | deepseek-v4-pro / v4-flash | 官方直连 |
| 硅基流动 SiliconFlow | `https://api.siliconflow.cn/v1` | DeepSeek（V4-Pro / V4-Flash / V3.2 / R1）、Qwen（Qwen3.6 / Qwen3.5）、GLM（GLM-5.1 / GLM-4.7）、Kimi（Kimi-K2.6） | 一个 Key 换多家模型，适合对比选型 |

**故障转移机制**（`core/llm/openai_compatible.py` + `LLM_FAILOVER` 配置）：
- 备用端点链：`LLM_FAILOVER="base_url|api_key|model;base_url|api_key|model"`，按序尝试；
- 切换触发条件：连接失败 / 超时 / 429 限流 / 5xx 服务故障 / **401、403 密钥失效**（主端点 Key 坏了切到有效备端点可恢复服务）；400 等请求本身的问题不切换（换端点同样失败）；
- 流式接口：首个片段返回前的异常可切换；已开始输出则直接抛错——**避免内容重复**；
- 每次切换记录 warning 日志，管理后台状态页展示备用端点模型列表。

**当前配置**：小米 MiMo（`mimo-v2.5-pro`）主端点 + DeepSeek v4-flash 备用，实测主端点直连正常、SSE 流式 21 个 delta 正常推送。

## 二、面试官高频问题与参考答案

### A. RAG 与检索

**Q1：为什么做混合检索？只用向量检索不行吗？**
> 不行。向量检索擅长语义相似，但对专有名词、缩写、型号这类精确关键词召回差——比如用户查 "L/C"，语义上和 "信用证支付流程" 很近但字面不匹配，纯向量可能漏召回。BM25 恰好相反。外贸场景术语和型号密集，所以我用向量 + BM25 双路召回，各取 top_k×3，再用 RRF 融合。实测我们知识库里"订单什么时候发货"这类查询，两路各自命中的片段在融合后排名都更稳。

**Q2：RRF 的原理？为什么用它而不是加权求和？**
> RRF（倒数排名融合）对每个候选按 `Σ weight/(k+rank)` 计分，k 取 60。核心优势是**只用排名、不用原始分数**——向量余弦分在 0~1，BM25 分无上界，量纲不可比，直接加权会被某一方的分数量纲支配。RRF 天然归一化了双方贡献。

**Q3：chunk 大小怎么定的？重叠为什么是 128？**
> 500 字/128 重叠是起点经验值：太小语义不完整，太大检索粒度粗、且挤占 Prompt 上下文。重叠是为了避免关键信息正好被切在边界。我的分块器优先按段落和句子边界切，只有超长单句才硬切，尽量不破坏语义。更精细的做法（按 token 数、按标题层级结构切分）是后续优化方向，这个答案的关键是展示"知道这是个需要评测调优的参数"。

**Q4：怎么解决大模型幻觉？**
> 三层：第一层 RAG 本身——回答必须基于检索到的知识片段，系统提示词明确"知识库无相关信息时如实说明并建议转人工"；第二层**溯源**——每个回答附带来源文件、相似度和片段摘要，用户可核对；第三层**转人工兜底**——关键词规则识别投诉、退款、法律等高风险意图，不交给模型。检索质量层面靠混合检索 + 重排序提升召回准确率。

**Q5：怎么评估检索质量？**
> 我自建了 52 条外贸场景问答评测集（覆盖同义改写、英文关键词，标注相关问题应命中的 chunk），离线跑 Recall@K / MRR 建基线——当前 Recall@3 = 100%、MRR = 0.981（`scripts/eval_rag.py` 可一键复跑）。这套评测还驱动了权重调优：实验定位到「Mock Embedding 下向量路是噪声源」，把向量/BM25 融合比从 0.6/0.4 调到 0.4/0.6，Recall@3 从 96.2% 提到 100%。后续接真实 Embedding 后要重跑重调。核心方法论：RAG 不看评测集调参数就是盲调。

**Q6：重排序为什么需要？现在的实现是什么？**
> 召回阶段追求"不漏"（宁多勿少），排序阶段追求"准"。我们先用启发式（关键词覆盖率 + 向量分加权）跑通链路，接口按 `rerank(query, items)` 抽象好了，生产替换为 bge-reranker 交叉编码器或 Cohere rerank 只需改一个函数——交叉编码器对 query 和文档做联合编码，精度远高于双塔式召回分。

### B. 工程与并发

**Q7：SSE 和 WebSocket 怎么选的？为什么？**
> 客服问答只需要服务器→客户端单向流式推送，选 SSE：纯 HTTP 不需要协议升级、穿过网关/代理和 CORS 处理都更简单、浏览器 EventSource/fetch 都能消费、自带断线重连语义。WebSocket 适合双向低延迟场景（语音、协作编辑），这里用它是过度设计。

**Q8：流式接口怎么实现落库的？有什么坑？**
> LLM 层封装 `generate_stream` 逐段产出；接口层先做完意图识别和检索（这两步快），再逐段推 delta，结束时推一个 meta 事件（意图、溯源、耗时）并落库。最大的坑：**FastAPI 依赖注入的数据库会话在流式响应结束时就关闭了**，生成器的落库必须用自己新建的 Session。另外每段 delta 要累计成完整回答再存储。

**Q9：asyncio.gather 并发调用 LLM，数据库会话会不会有问题？**
> SQLAlchemy Session 非线程安全，但这里安全：asyncio 事件循环是单线程的，协程只在 `await` 处发生切换，每个协程内的 `db.add/commit` 是同步连续执行的，不会交错。如果换成多线程并发就需要每线程独立 Session（`sessionmaker` 每次 `SessionLocal()` 本身就是新建会话）。用量的 ApiUsage 记录我在 gather 完成后统一 add + 单次 commit，也把事务粒度收敛了。

**Q10：你说检索做了缓存，缓存失效怎么保证不出错？**
> 关键是把失效挂在**写路径**上而不是靠 TTL：文档上传/删除的代码路径里显式调用 `invalidate_bm25_cache()`，向量矩阵在 add/delete/加载后置 None 惰性重建。读路径 O(1) 命中，写路径重建一次。 BM25 缓存还带了语料指纹校验（全部 chunk id 的元组做 key），即使万一失效调用遗漏，指纹变化也会导致 miss 而不是脏读——**宁可重建也不能返回旧结果**。

**Q11：单一大模型同时服务多个场景，怎么保证响应速度？**
> 四个手段：① 长任务**并发化**——文案 4 段 asyncio.gather，延迟从串行之和降为最慢一段；② **流式**——客服 SSE 先出首字，体感等待从"全文生成完"变成"不到 1 秒"；③ **缓存**——翻译记忆两级缓存，重复文本零模型调用；④ **检索侧降耗**——BM25/向量矩阵缓存把非模型开销压到毫秒级。再往上是限流配额和高频问答缓存（已列入待办）。

### C. 安全

**Q12：JWT 的结构和你项目里的实现？**
> 三段式：header（算法）、payload（sub/exp/iat）、signature（对前两段 HMAC-SHA256）。我项目里是基于标准库手写的：签名用 `hmac.new(secret, signing_input, sha256)`，校验时 `hmac.compare_digest` 防时序攻击，再验 `exp`。密码存储用 PBKDF2-HMAC-SHA256、10 万轮、每用户独立随机盐——加盐防彩虹表，多轮提高暴力破解成本。没用 pyjwt/passlib 是脚手架阶段零依赖的取舍，生产可以平滑替换，接口不变。

**Q13：讲一个你发现并修复的安全漏洞。**
> 代码评审发现注册接口直接信任客户端传的 `role` 字段——任何人 POST `{"role":"admin"}` 就能自助提权，这是典型的**水平/垂直越权**。修复三件事：注册时服务端强制 `operator`、schema 里删掉 role 字段（让"客户端可以指定角色"这件事在契约上就不存在）、新增 `grant-role` 接口且要求当前用户为 admin（非 admin 返回 403）。教训是：**权限类字段永远不能信任客户端输入**。

**Q14：CORS 为什么 `*` 和 `allow_credentials=True` 不能同时用？**
> 浏览器规范直接禁止这个组合：凭据（Cookie、Authorization）意味着跨站携带用户身份，如果允许任意源携带凭据读取响应，就等于对全网开放了用户会话。所以浏览器对带凭据的请求要求 `Access-Control-Allow-Origin` 必须是**具体源**。我项目里做了自适应：白名单模式开凭据，通配符演示模式自动降级关闭凭据。

### D. 数据与架构

**Q15：为什么用 SQLite？什么时候必须换？**
> 脚手架阶段 SQLite 零运维、单文件、够用；SQLAlchemy 屏蔽了方言差异，换 PostgreSQL 改 `DATABASE_URL` 即可。必须换的时机：多实例部署（SQLite 是文件锁，写并发差）、需要 PG 的 pgvector/JSONB 等能力、数据量或并发上量。向量库同理——内存版（JSON 持久化）适合演示，生产切 Chroma/Milvus，接口已隔离。

**Q16：加了一列数据库字段，已有用户的库怎么办？**
> 早期用轻量迁移：`init_db` 里 `create_all` 只建新表不改旧表，对已存在的表用 `inspect` 检查列、缺列就 `ALTER TABLE ADD COLUMN` 并补索引（比如 `knowledge_docs.doc_id` 就是这么加的）。后来演进到 **Alembic**：已有两个版本化迁移——初始迁移建 8 张表、第二个迁移给 `knowledge_docs`/`conversations` 加 `tenant_id` 并回填存量行，空库 upgrade/downgrade 验证通过、现有库 stamp。加一列字段的正确姿势就是写迁移脚本，可版本化、可回滚。

**Q17：这个系统的可插拔设计讲一下？**
> 四个外部能力（LLM/Embedding/向量库/Agent）各自抽象出 base 接口 + 工厂函数，实现按 `.env` 配置选择。两个收益：一是 **Mock 降级**——没配 Key 自动回退 Mock 实现，无外网环境全链路可跑，测试和演示稳定；二是**换供应商零代码改动**——我们的 `openai_compatible` 实现同时兼容 DeepSeek/通义千问/OpenAI/Moonshot，改配置即切换。本质是把"不确定性最高的外部依赖"收敛到确定性的接口后面。

### E. 开放性问题

**Q18：这个项目里你最有成就感/最难的一个点？**
> 建议讲"检索性能优化 + 流式改造"组合拳：先定位到每次查询全量重建 BM25 和重拼向量矩阵的性能隐患（数据量增长后必然劣化），用语料指纹缓存 + 归一化矩阵缓存解决，失效挂在写路径；再把同步问答改造成 SSE 流式，包括 LLM 层流解析、独立会话落库、前端 ReadableStream 手动分帧——一个功能串起了后端、前端、协议、数据四层，还踩了"依赖注入会话提前关闭"这种有代表性的坑。

**Q19：如果用户量涨 10 倍，先改什么？**
> 按顺序：① 数据库 SQLite → PostgreSQL，向量库内存 → Chroma/Milvus（配置即切，改动最小）；② 加 Redis 承接翻译记忆/会话/高频问答缓存，BM25 索引随实例数复制问题也顺带解决；③ uvicorn 多 worker + 限流配额控制 LLM 成本；④ 接监控（延迟 P95、Token 消耗、转人工率）看瓶颈在哪再继续。架构本身不用推翻——分层和可插拔就是为这一天准备的。

**Q20：如实说明未完成的部分（防翻车准备）**
> 主动说清边界反而加分：「重排序当前是启发式打分，接口按 `rerank(query, items)` 抽象好了，生产可平滑替换 bge-reranker 交叉编码器（L1 待办）；向量库当前是内存版 + Chroma，生产上量切 Milvus；RAG 评测集基于 Mock Embedding 建基线，接真实 Embedding 后要重跑重调权重；SSE 路径的 Token 统计是估算值，后续用 stream_options 拿真实用量。」——每一项都知道是什么、为什么、计划怎么补，比假装全做完可信得多。

### F. 高可用与模型策略

**Q21：大模型服务是外部依赖，怎么保证它不中断你的业务？**
> 我做了三层防线。第一层**多端点故障转移**：配置备用端点链（主端点小米 MiMo、备用 DeepSeek），主端点连接失败、超时、限流或密钥失效时自动按序切换，全部实现于一个 `openai_compatible` 协议层，各厂商无缝兼容；流式接口在首片段前可切换、开始输出后不再切换（避免内容重复）。第二层**Mock 降级**：所有端点不可用时框架仍可跑通（Mock 实现），管理后台可见当前实现，排查有抓手。第三层**可观测**：每次切换记 warning 日志，管理后台展示端点链与模型列表。顺带的收益是换厂商 = 改三行配置，不同任务可以选不同性价比的模型。

**Q22：接入了这么多模型，实际怎么选型？**
> 按任务特性选：客服问答重响应速度和成本，用轻量快速的模型（如 deepseek-v4-flash / mimo 轻量档）；文案创作重质量，用旗舰档（v4-pro / mimo-v2.5-pro）；推理类任务用带推理能力的模型。我的平台支持按任务传 `task` 参数（chat/translation/copywriting），这个参数目前用于 Mock 策略，预留了「按任务路由到不同模型」的扩展位。选型决策同样应该用数据：拿评测集在候选模型上各跑一遍，对比质量、延迟、单次成本三个维度再定，而不是看榜单拍脑袋。

## 三、回答技巧备忘

1. **结构化回答**：结论先行 → 为什么 → 项目里怎么做的 → 效果/取舍。避免一上来背概念。
2. **每个答案都落在自己代码上**：说出文件名和函数（如 "RRF 在 `retriever.py`，k=60"），可信度完全不同。
3. **主动讲取舍**：面试官考察的不是"你用了什么"而是"你为什么不用别的"（SSE vs WebSocket、RRF vs 加权、SQLite vs PG）。
4. **不知道就承认 + 给方法**："这个我没实测过，但我会这样验证：……" 远好于编造数据。
