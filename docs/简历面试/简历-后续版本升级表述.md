# 简历中如何表述「后续版本升级」

> 背景：渠道对接（亚马逊等）**只推进到设计层**，代码未落地。目标是既体现架构前瞻性，又不构成造假。
> 核心原则：用**产出物**支撑「设计」二字——你有 V2.0 方案 + P0/P1/P2 三份推进文档，这是可展示的证据，不是空话。

## 一、先说结论：怎么写才安全

| 写法 | 风险 | 建议 |
|---|---|---|
| ❌ "对接亚马逊 SP-API，实现订单/商品同步" | 完成时态，属于造假 | 禁用 |
| ❌ "负责多平台渠道对接" | 暗示已做，追问即穿 | 禁用 |
| ⚠️ "规划中的多平台对接能力" | 无产出物，像凑字数 | 不推荐 |
| ✅ "设计并输出多平台对接方案与分期推进文档" | 有真实产出物可展示 | **推荐** |

关键差别：**"设计"是已完成的动作，"对接"是想做的事**。你确实完成了设计，所以理直气壮写"设计"。

## 二、可直接粘贴的措辞（按你现有简历结构排版）

**① 追加到「核心实现」末尾（推荐，与现有条目同风格）：**

> 设计多平台渠道对接扩展方案：抽象渠道适配层（ChannelAdapter 契约 + 工厂注册 + Mock 兜底降级），统一商品/订单/Listing 数据契约与幂等落库键；规划 LWA OAuth 令牌自动刷新、令牌桶限流与 429 指数退避、PII 合规取数与增量同步断点续传，输出 P0–P2 分期推进文档。

**② 在项目末尾单列一行（信息密度更高，适合版面紧张）：**

> 后续版本（V2.0）：接入亚马逊 SP-API / Shopify 等平台，打通「平台数据 → AI 加工 → 回写平台」运营闭环；已完成架构设计与分期方案。

**③ 面试口头版（60 秒，被问到时用）：**

> "平台对接我做到了设计层：渠道抽象层、OAuth 令牌管理、限流退避、合规取数、增量续传都做了详细设计，方案和分期文档都输出了，P0 阶段的 Mock 全链路设计成不依赖任何凭证就能跑通。真实对接没落地是因为需要卖家账号和 Private App 审核——这是外部依赖，不是技术阻塞，代码可以先用沙箱环境完成。"

## 三、为什么这样写是「加分」而不是「心虚」

面试官对"未来规划"类内容的判断标准只有一个：**你是不是真的想过，还是抄来的关键词**。你的方案里有大量只有真做过设计才会有的细节，被追问时直接甩这些：

| 追问 | 你的回答（均有文档支撑） |
|---|---|
| "为什么要抽象一层？" | 复刻现有 LLM/向量库的可插拔模式，新增平台只加实现类，业务代码零改动 |
| "同步怎么防重复？" | 幂等键 `account_id + channel_id` 唯一索引 + upsert，重复执行不产生脏数据 |
| "限流怎么处理？" | 按接口配令牌桶（只用到平台上限 70% 留余量）+ 429 指数退避带 jitter |
| "断网了怎么办？" | 游标持久化在 `sync_jobs.cursor`，任务失败不推进游标，恢复后从断点继续 |
| "买家信息合规吗？" | 必须走 RDT 单独授权，本地只落 masked 字段，明文不落库不落日志 |
| "凭什么说能跑通？" | P0 阶段 Mock 实现保证零凭证全链路可跑，架构先立住 |

**甚至可以主动给面试官看方案文档**——这比任何形容词都有说服力。这是你和其他候选人最大的差别：别人说"我准备做"，你说"设计已完成，这是文档"。

## 四、必须避开的三个坑

1. **不要放在"亮点"位置。** 放在核心实现末尾或单独规划行；简历最前面是已完成的硬成果（RAG / 评测 / 并发优化），规划类内容抢位会显得虚。
2. **不要写具体平台功能的完成时。** "实现 Amazon Orders API 对接"不行；"规划 Amazon Orders/Catalog/Listings 三域接入"可以。
3. **不要说"下一版就上线"这类承诺。** 说"已完成设计，落地取决于账号审核等外部条件"——把不确定性讲清楚反而显专业。

**面试口径（被问"哪 30 个、怎么验证的"照此答）**：
- 实现方式：语言码透传 LLM，不依赖本地枚举；内置 11 种常用语种名映射兜底。
- 验证方式：常规语种走映射；另抽 sw / th / pl / uk 四个非常用语种实测，`translate()` 均正常返回。
- 诚实边界：当前为**机制层验证**；翻译质量需真实 LLM Key 才能系统评估，被追问时如实说明即可，不影响"30+ 语种可翻译"的表述成立。

其余表述与代码完全咬合，可以放心投（除"25 项测试全绿"需先处理 402 欠费问题）。
