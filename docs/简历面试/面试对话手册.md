# 面试对话手册 —— 跨境电商一站式智能服务平台

> 用法：开场白与各主题"第一问"背熟，追问理解逻辑即可（逐字背一听就穿）。
> 口径均与代码逐字核对，被要求翻代码时按文末速查表打开。

## 0. 开场白（60 秒，背熟）

> "面向外贸企业的多语言智能服务平台，解决业务员同时应付多语言客服、文案和翻译的人力问题，共六大模块：文案生成、多语言翻译、RAG 智能客服、知识库、数据洞察、后台管理。
> 三个下功夫的点：RAG 是 BM25 加向量双路召回、RRF 融合再重排序，配了离线评测脚本做质量回归；全链路可插拔，LLM / Embedding / 向量库接口隔离，无 Key 降级 Mock，克隆即跑通；鉴权用标准库手写 PBKDF2 加 JWT，零第三方安全依赖。
> 前后端分离，后端 FastAPI 分 api / services / core / db 四层，前端 Vue 3。"

## 1. 主题 A：RAG 检索链路（最高频）

**Q 讲一下检索链路？**
> 向量管语义相似，BM25 管关键词精确匹配——外贸场景 SKU、型号这类术语向量常糊掉，BM25 补短板。两路 RRF 融合（k=60）后过一层重排序，取 top_k 返回并带知识溯源，能标注引用文档。

**Q RRF 是什么？为什么不用加权平均？**
> 倒数排名融合，对文档在各路结果里的名次取倒数求和，k=60 是平滑项。不用加权平均是因为 BM25 分数和余弦相似度量纲不同，直接加权等于让量纲大的说了算；RRF 只看名次，天然规避。代码保留了权重参数，**配置默认向量 0.4 / BM25 0.6**（`HYBRID_WEIGHT_VECTOR/BM25`，注意构造函数里的 0.6/0.4 只是形参默认值，运行时被配置覆盖——2026-09-17 核对过 `get_retriever`）。

**Q 召回候选量怎么定？**
> 向量侧先取 top_k 三倍、上限 50，给租户过滤和重排序留余量——这两步都会丢候选，不扩容最终 top_k 会不足。

**Q BM25 索引怎么维护？**
> 进程内缓存，key 是租户加语料指纹（当前语料全部文档 ID 的元组）。知识库增删时 knowledge 服务调 `invalidate_bm25_cache` 失效，下次检索重建；缓存只留最新一份，防并发增删堆积。

**Q 多租户怎么做的？**
> 先召回后过滤：向量结果与 BM25 候选都按 metadata 的 tenant_id 过滤，未标记的视为 default 租户；BM25 缓存指纹含租户，防串索引。

**Q 重排序怎么实现的？**
> 两种实现配置切换：默认 heuristic（关键词覆盖率与检索得分五五开加权，零依赖）；配 cross_encoder 走 sentence-transformers 的 CrossEncoder（BGE reranker），联合编码打分精度更高，加载失败自动回退。内部打分字段返回前 pop 掉，不泄漏到 API。

## 2. 主题 B：评测（加分题）

**Q 怎么证明检索效果好？**
> 写了离线评测脚本 `eval_rag.py`：评测集是 JSON case 列表，每条含 query 和 must 关键词（返回片段含全部关键词算命中），算 Recall@K、MRR、平均耗时，改检索参数就跑一遍做回归。脚本直跑即可——memory 向量库带 JSON 持久化（`data/index/vector_store.json`），重启不丢数据。

**Q 评测集多大？Recall 多少？**
> ⚠️ 诚实口径：围绕示例知识库手工构造的小集合，价值在**固化回归流程**而非统计显著；所以简历文本不写具体召回率——样本太小，写进简历就是误导。

📌 **实测参考值（2026-09-17，直接跑 `python scripts/eval_rag.py --topk 3`）**：
Recall@3 = 52/52 = **100%**，MRR@3 = **0.942**，平均耗时 <1ms；Recall@5 同为 100%。
注意：这是 52 条小集合 + 示例知识库 + mock embedding（BM25 主导）的结果，只能口头说"当前小评测集上全命中"，**别说成系统召回能力 100%**——面试官会立刻追问"是不是评测集太简单"，正确接法是承认并引到"计划扩集 + 人工标注"（见下问）。

**Q 怎么做得更严谨？**
> 扩到几百条、人工标注相关性替代关键词命中、加 LLM-as-judge 评答案质量；目前端到端回答质量还没有自动评测。

## 3. 主题 C：可插拔架构（高频）

**Q 可插拔具体指什么？**
> 三类外部能力全接口隔离：LLM（mock / openai_compatible，配 Base URL 可接 DeepSeek、通义等）、Embedding 同理、向量库（memory / chroma）。切换只改配置，业务代码不动。

**Q 为什么默认 Mock？不玩具吗？**
> 刻意的交付设计：Mock 保证克隆即跑、CI 可测、演示不依赖外部服务；核心价值在检索与编排，LLM 只是末端生成器。真实 Key 在 `.env`（已 git 忽略），一行配置切 DeepSeek。

**Q 配置怎么管理？**
> pydantic-settings 集中在 `config.py`，`.env` 覆盖默认；另有 `check_config.py` 自检脚本，一跑就打印当前生效实现。

## 4. 主题 D：Agent / LangGraph（注意措辞）

**Q Agent 怎么做的？**
> 默认规则路由：query 做意图分类（客服咨询 / 订单查询 / 翻译 / 转人工）分发对应流程，另有 need_human 判断触发人工转接。装了 langgraph 后升级为图编排：StateGraph 以 classify 为入口，挂条件边路由到四个业务节点。

**Q（追问）图上节点里做什么？**
> ⚠️ 易翻车：图的骨架与路由逻辑完整真实，业务节点目前是规则占位，完整逻辑在 `workflow.py`。设计意图是先把编排结构立住，节点实现逐步替换为真实调用。**别说成"已完成的多智能体系统"**（节点返回占位字符串，翻代码即穿），也别说 Supervisor（项目里没有）。

**Q 为什么规则路由，不让 LLM 分类？**
> 脚手架阶段规则零成本、确定性高、可测试。生产路径：LLM 分类加 Few-shot，规则兜底，置信度低时默认走 RAG 问答。

## 5. 主题 E：鉴权与安全

**Q 为什么自己写 JWT？**
> 依赖最小化，且值得手写一遍：标准库 hmac/hashlib 完成 PBKDF2 带盐哈希与 HS256 签发校验。写完对攻击面理解更深——alg 不能信、密钥强度、时钟偏移。生产会换成熟库，自写适合学习与小场景。

**Q 默认密码 admin123 不安全？**
> 演示模式播种的默认管理员，README 标注生产必须改；生产开 `AUTH_REQUIRED=true` 后接口全部要求 Bearer token。

## 6. 主题 F：翻译与术语库

**Q 翻译模块亮点？**
> 持久化术语库。外贸痛点不是通用翻译而是术语一致性——同一 SKU 名不能这次译 A 下次译 B。术语存表随知识库增量更新，翻译时先查术语强制替换再走 LLM，保证跨语种一致，另有术语管理接口。

## 7. 主题 G：工程化与交付

**Q 怎么部署交付？**
> 开发用一键启动器：依赖哈希缓存（requirements.txt / package.json 未变则跳过安装）秒级启动，支持 start/stop/restart/status；停止按端口反查 PID 结束进程，端口占用会展示进程并交互式释放。部署有 Docker Compose 与生产编排文件。

**Q 启动器有什么技术点？**
> 内容哈希依赖缓存、netstat 端口反查 PID、健康检查探活。真实踩坑：中文 Windows 下 netstat 输出是 GBK，按 UTF-8 解码直接崩，改为字节流容错解码；wmic 在新系统弃用，换 PowerShell CIM 查询。这类具体踩坑比八股有印象。

## 8. 主题 H：平台对接（防坑）

**Q 有没有对接亚马逊这类平台？**
> 真实对接未落地，但架构有预留且思路讲得清：加 ChannelAdapter 抽象层统一商品 / 订单 / Listing 契约，与现有 LLM 抽象同一套模式；亚马逊走 SP-API，难点在 LWA OAuth 令牌自动刷新、各接口独立限流需令牌桶加 429 指数退避、订单买家 PII 要脱敏。贵司有需求可直接叠加实现。
> **千万不要**顺着说"对接过"——SP-API 审核流程、RDT 机制一问就穿。
